# Интернет-магазин «Web-Larёk»
«Web-Larёk» — это интернет-магазин с товарами для веб-разработчиков, где пользователи могут просматривать товары, добавлять их в корзину и оформлять заказы. Сайт предоставляет удобный интерфейс с модальными окнами для просмотра деталей товаров, управления корзиной и выбора способа оплаты, обеспечивая полный цикл покупки с отправкой заказов на сервер.
Для просмотра информации и оформления заказа используются модальные окна.

## Архитектура приложения

Код приложения разделен на слои согласно парадигме MVP (Model-View-Presenter), которая обеспечивает четкое разделение ответственности между классами слоев Model и View. Каждый слой несет свой смысл и ответственность:

Model - слой данных, отвечает за хранение и изменение данных.  
View - слой представления, отвечает за отображение данных на странице.  
Presenter - презентер содержит основную логику приложения и  отвечает за связь представления и данных.

Взаимодействие между классами обеспечивается использованием событийно-ориентированного подхода. Модели и Представления генерируют события при изменении данных или взаимодействии пользователя с приложением, а Презентер обрабатывает эти события используя методы как Моделей, так и Представлений.

## Базовый код

### Класс Component
Является базовым классом для всех компонентов интерфейса.
Класс является дженериком и принимает в переменной `T` тип данных, которые могут быть переданы в метод `render` для отображения.

Конструктор:  
`constructor(container: HTMLElement)` - принимает ссылку на DOM элемент за отображение, которого он отвечает.

Поля класса:  
`container: HTMLElement` - поле для хранения корневого DOM элемента компонента.

Методы класса:  
`render(data?: Partial<T>): HTMLElement` - Главный метод класса. Он принимает данные, которые необходимо отобразить в интерфейсе, записывает эти данные в поля класса и возвращает ссылку на DOM-элемент. Предполагается, что в классах, которые будут наследоваться от `Component` будут реализованы сеттеры для полей с данными, которые будут вызываться в момент вызова `render` и записывать данные в необходимые DOM элементы.  
`setImage(element: HTMLImageElement, src: string, alt?: string): void` - утилитарный метод для модификации DOM-элементов `<img>`


### Класс Api
Содержит в себе базовую логику отправки запросов.

Конструктор:  
`constructor(baseUrl: string, options: RequestInit = {})` - В конструктор передается базовый адрес сервера и опциональный объект с заголовками запросов.

Поля класса:  
`baseUrl: string` - базовый адрес сервера  
`options: RequestInit` - объект с заголовками, которые будут использованы для запросов.

Методы:  
`get(uri: string): Promise<object>` - выполняет GET запрос на переданный в параметрах ендпоинт и возвращает промис с объектом, которым ответил сервер  
`post(uri: string, data: object, method: ApiPostMethods = 'POST'): Promise<object>` - принимает объект с данными, которые будут переданы в JSON в теле запроса, и отправляет эти данные на ендпоинт переданный как параметр при вызове метода. По умолчанию выполняется `POST` запрос, но метод запроса может быть переопределен заданием третьего параметра при вызове.  
`handleResponse(response: Response): Promise<object>` - защищенный метод проверяющий ответ сервера на корректность и возвращающий объект с данными полученный от сервера или отклоненный промис, в случае некорректных данных.

### Класс EventEmitter
Брокер событий реализует паттерн "Наблюдатель", позволяющий отправлять события и подписываться на события, происходящие в системе. Класс используется для связи слоя данных и представления.

Конструктор класса не принимает параметров.

Поля класса:  
`_events: Map<string | RegExp, Set<Function>>)` -  хранит коллекцию подписок на события. Ключи коллекции - названия событий или регулярное выражение, значения - коллекция функций обработчиков, которые будут вызваны при срабатывании события.

Методы класса:  
`on<T extends object>(event: EventName, callback: (data: T) => void): void` - подписка на событие, принимает название события и функцию обработчик.  
`emit<T extends object>(event: string, data?: T): void` - инициализация события. При вызове события в метод передается название события и объект с данными, который будет использован как аргумент для вызова обработчика.  
`trigger<T extends object>(event: string, context?: Partial<T>): (data: T) => void` - возвращает функцию, при вызове которой инициализируется требуемое в параметрах событие с передачей в него данных из второго параметра.

## Данные

В приложении используются две основные сущности, описывающие данные: товар и покупатель. Для описания этих данных используются интерфейсы `IProduct` и `IBuyer`. Также используется тип `TPayment`, который определяет доступные способы оплаты(card/cash).

### Интерфейс IProduct

Интерфейс `IProduct` описывает данные одного товара, которые используются в каталоге, при просмотре подробной информации о товаре и в корзине.

/*
interface IProduct {
  id: string;
  description: string;
  image: string;
  title: string;
  category: string;
  price: number | null;
}*/

Поля интерфейса:

id: string — уникальный идентификатор товара;
description: string — описание товара;
image: string — имя или путь к изображению товара;
title: string — название товара;
category: string — категория товара;
price: number | null — цена товара. Значение null означает, что товар недоступен для покупки.

### Интерфейс IBuyer
Интерфейс IBuyer описывает данные покупателя, необходимые для оформления заказа.

/*interface IBuyer {
  payment: TPayment | null;
  email: string;
  phone: string;
  address: string;
}*/

Поля интерфейса:

payment: TPayment | null — выбранный способ оплаты. До выбора способа оплаты поле имеет значение null.
email: string — электронная почта покупателя;
phone: string — телефон покупателя;
address: string — адрес доставки.

### Тип TPayment
Тип TPayment определяет доступные способы оплаты заказа.

//type TPayment = 'card' | 'cash';
card — оплата картой;
cash — оплата при получении.

### Интерфейс `IProductsResponse`

Интерфейс `IProductsResponse` описывает ответ API при получении каталога:
interface IProductsResponse {
    total: number;
    items: IProduct[];
}

`total: number` — общее количество товаров.
`items: IProduct[]` — массив товаров.

### Интерфейс `IOrderRequest`

Интерфейс `IOrderRequest` описывает данные, отправляемые серверу при оформлении заказа:
interface IOrderRequest extends IBuyer {
    items: string[];
    total: number;
}
Интерфейс расширяет `IBuyer` и дополнительно содержит:

`items: string[]` — идентификаторы товаров в заказе.
`total: number` — общая стоимость заказа.

### Интерфейс `IOrderResponse`

Интерфейс `IOrderResponse` описывает результат успешного оформления заказа:
interface IOrderResponse {
    id: string;
    total: number;
}

`id: string` — идентификатор оформленного заказа.
`total: number` — итоговая стоимость заказа.

## Модели данных

В приложении используются три модели данных:

Catalog — хранение товаров, которые можно купить в приложении;
Basket — хранение товаров, которые пользователь выбрал для покупки;
Buyer — данные покупателя, которые тот должен указать при оформлении заказа.

Модели отвечают только за хранение и работу с данными.

При изменении данных Модель генерирует событие через общий экземпляр `EventEmitter`.

### Класс Catalog
Класс Catalog отвечает за хранение массива всех товаров и товара, выбранного пользователем для подробного отображения.

Конструктор
constructor(events: IEvents) — принимает экземпляр брокера событий, который используется для генерации событий при изменении данных каталога.

Поля класса
products: IProduct[] — массив всех товаров, доступных в каталоге;
selectedProduct: IProduct | null — товар, выбранный для подробного отображения. Если товар не выбран, значение равно null.
events: IEvents — брокер событий приложения.

Методы класса
`setProducts(products: IProduct[]): void` — сохраняет массив товаров и генерирует событие `catalog:changed`.

`getProducts(): IProduct[]` — возвращает массив товаров.

`getProductById(id: string): IProduct | undefined` — возвращает товар по идентификатору либо `undefined`, если товар не найден.

`setSelectedProduct(product: IProduct): void` — сохраняет выбранный товар и генерирует событие `catalog:selected`.

`getSelectedProduct(): IProduct | null` — возвращает выбранный товар либо `null`.

### Класс Basket
Класс Basket отвечает за хранение товаров, выбранных покупателем для покупки.

Конструктор
constructor(events: IEvents) — принимает экземпляр брокера событий, который используется для генерации события при изменении содержимого корзины.

Поля класса
items: IProduct[] — массив товаров, выбранных покупателем для покупки (добавленных покупателем в корзину)
events: IEvents — брокер событий приложения.

Методы класса
`getItems(): IProduct[]` — возвращает товары корзины.
`addItem(product: IProduct): void` — добавляет товар, если его ещё нет в корзине. При изменении данных генерируется событие `basket:changed`.
`removeItem(product: IProduct): void` — удаляет товар из корзины. При изменении данных генерируется событие `basket:changed`.
`clear(): void` — очищает корзину. При изменении данных генерируется событие `basket:changed`.
`getTotalPrice(): number` — возвращает общую стоимость товаров.
`getCount(): number` — возвращает количество товаров.
`hasItem(id: string): boolean` — проверяет наличие товара по идентификатору.
`clear(): void` — очищает корзину и генерирует событие `basket:changed`.

### Класс Buyer
Класс Buyer отвечает за хранение и валидацию данных покупателя, необходимых для оформления заказа.

Конструктор
`constructor(events: IEvents)` — принимает брокер событий.

Поля класса
data: IBuyer — объект с данными покупателя. Хранит выбранный способ оплаты, адрес доставки, email и телефон. При создании экземпляра класса и после вызова метода clear() поле инициализируется начальными значениями: строковые поля содержат пустую строку (''), а поле payment — значение null, что означает, что способ оплаты ещё не выбран.
events: IEvents — брокер событий приложения.

Методы класса
`setData(data: Partial<IBuyer>): void` — обновляет одно или несколько полей данных покупателя и генерирует событие `buyer:changed`.
`getData(): IBuyer` — возвращает текущие данные покупателя.
`clear(): void` — сбрасывает данные к начальному состоянию и генерирует событие `buyer:changed`.
`validate(): IBuyerValidationErr` — выполняет валидацию данных.
Поле `payment` считается валидным, если выбран способ оплаты.
Поля `address`, `email` и `phone` считаются заполненными, если после вызова `trim()` значение не является пустой строкой.

Пример результата работы метода validate():

{
  payment: 'Не выбран вид оплаты',
  email: 'Укажите емэйл',
}

В данном примере способ оплаты и email не заполнены, поэтому для них возвращаются сообщения об ошибках. Остальные поля прошли проверку.

## Слой коммуникации
Слой коммуникации отвечает за взаимодействие приложения с сервером. Для выполнения HTTP-запросов используется базовый класс Api, который передаётся в класс WebLarekApi через конструктор.

### Класс WebLarekApi
Класс WebLarekApi является представителем коммуникационного слоя и использует композицию с классом Api.

Конструктор:
constructor(api: IApi) — принимает объект, реализующий интерфейс IApi.

Поле класса:
api: IApi — объект базового API, используемый для выполнения GET- и POST-запросов.

Методы:
getProducts(): Promise<IProductsResponse> — выполняет GET-запрос на эндпоинт /product/ с помощью метода get класса Api и возвращает объект с общим количеством товаров и массивом товаров.
createOrder(data: IOrderRequest): Promise<IOrderResponse> — выполняет POST-запрос на эндпоинт /order/. В запрос передаются данные покупателя, идентификаторы выбранных товаров и общая стоимость заказа. Метод возвращает объект с идентификатором заказа и его стоимостью.

Для типизации данных используются существующие интерфейсы IProduct и IBuyer. Тип IProductsResponse содержит массив товаров IProduct[], тип IOrderRequest расширяет IBuyer и содержит данные выбранных товаров и общую стоимость заказа, а IOrderResponse описывает ответ сервера после оформления заказа.

Для формирования полного адреса API используется константа `API_URL`.

Для формирования полного URL изображений используется константа `CDN_URL`.

## Слой представления (View)

Слой Представления отвечает за отображение данных и обработку действий пользователя.

Компоненты Представления не обращаются напрямую к Моделям и не изменяют данные приложения.

Все данные для отображения передаются компонентам Презентером.

В ответ на действия пользователя View-компоненты генерируют события через брокер событий.

Все компоненты наследуются от `Component<T>` непосредственно либо через базовые классы `Card` и `Form`.

### Иерархия компонентов

```text
Component<T>
│
├── Header
├── Gallery
├── Modal
├── Basket
├── Success
│
├── Card
│   ├── CardCatalog
│   ├── CardPreview
│   └── CardBasket
│
└── Form
    ├── OrderForm
    └── ContactsForm
```

`Modal` является самостоятельным компонентом.
От `Modal` не наследуются другие компоненты.

Компоненты `CardPreview`, `Basket`, `OrderForm`, `ContactsForm` и `Success` могут использоваться как содержимое модального окна.

## Основные компоненты Представления

### Класс `Header`

Компонент шапки страницы.
Отвечает за отображение количества товаров в корзине и обработку открытия корзины.
Наследуется от `Component<IHeaderData>`.

Конструктор

`constructor(events: IEvents, container: HTMLElement)`.
`events` — брокер событий.
`container` — корневой DOM-элемент `.header`.

Поля класса

`counterElement: HTMLElement` — элемент `.header__basket-counter`.
`basketButton: HTMLButtonElement` — кнопка `.header__basket`.
`events: IEvents` — брокер событий.

Методы/Сеттеры

`set counter(value: number)` — устанавливает количество товаров в корзине.

События

При нажатии на `.header__basket` генерируется событие `basket:open`.

### Класс `Gallery`

Компонент каталога товаров.
Наследуется от `Component<IGalleryData>`.

Конструктор

`constructor(container: HTMLElement)` — принимает элемент `.gallery`.

Данные для отображения

`catalog: HTMLElement[]` — массив готовых DOM-элементов карточек.

Методы/Сеттеры

`set catalog(items: HTMLElement[])` — заменяет содержимое галереи переданными карточками.
`Gallery` не создаёт карточки самостоятельно.
Карточки создаёт Презентер.

### Карточки товара

### Класс `Card`

Базовый класс всех карточек товара.
Наследуется от `Component<T>`.

Общий тип данных:
type TCardData = Pick<IProduct, 'title' | 'price'>;

Конструктор

`constructor(container: HTMLElement)` — принимает корневой DOM-элемент карточки.

Поля класса

`titleElement: HTMLElement` — DOM-элемент `.card__title`.
`priceElement: HTMLElement` — DOM-элемент `.card__price`.

Методы/Сеттеры

`set title(value: string)` — устанавливает название товара.
`set price(value: number | null)` — устанавливает стоимость товара.
Если значение `price` равно `null`, отображается текст `Бесценно`.
`Card` не хранит данные товара и не обрабатывает пользовательские действия.

### Класс `CardCatalog`

Карточка товара в каталоге.
Использует шаблон `#card-catalog`.
Наследуется от `Card<TCardCatalogData>`.
Тип `TCardCatalogData` создаётся на основе `TCardData` и части `IProduct`:
type TCardCatalogData =
    TCardData &
    Pick<IProduct, 'image' | 'category'>;

Конструктор

`constructor(events: IEvents, container: HTMLElement, productId: string)`.
`events` — брокер событий.
`container` — DOM-элемент карточки.
`productId` — идентификатор товара, используемый внутри обработчика клика. Он не сохраняется в поле класса.

Поля класса

`imageElement: HTMLImageElement` — элемент `.card__image`.
`categoryElement: HTMLElement` — элемент `.card__category`.

Методы/Сеттеры

`set image(value: string)` — устанавливает изображение товара.
`set category(value: string)` — устанавливает название категории и соответствующий CSS-модификатор из объекта `categoryMap`.

События

При нажатии на карточку генерируется событие `card:select`.

Передаваемые данные:
{
    id: string;
}

### Класс `CardPreview`

Полная карточка товара.
Использует шаблон `#card-preview`.
Наследуется от `Card<TCardPreviewData>`.

Тип данных:
type TCardPreviewData =
    TCardData &
    Pick<IProduct, 'image' | 'category' | 'description'> & {
        buttonDisabled: boolean;
        buttonText: string;
    };

Конструктор

`constructor(events: IEvents, container: HTMLElement, productId: string)`.
`events` — брокер событий.
`container` — DOM-элемент карточки.
`productId` — идентификатор товара, используемый обработчиком кнопки покупки. Не сохраняется в поле класса.

Поля класса

`imageElement: HTMLImageElement` — изображение товара.
`categoryElement: HTMLElement` — категория товара.
`descriptionElement: HTMLElement` — описание товара.
`buttonElement: HTMLButtonElement` — кнопка покупки.

Методы/Сеттеры

## Распределение ответственности в `MVP`

Общая схема взаимодействия:

```text
Действие пользователя
        │
        ▼
       View
        │
        │ событие
        ▼
    Presenter
        │
        ▼
      Model
        │
        │ событие изменения данных
        ▼
    Presenter
        │
        ▼
       View
```

Компоненты `View` не обращаются напрямую к Моделям.

Модели не знают о компонентах Представления.

Если для компонента необходимы данные из нескольких Моделей, Презентер получает их через публичные методы Моделей и формирует необходимые данные самостоятельно.

```text
Catalog ────┐
            │
Basket ─────┼──► Presenter ───► View
            │
Buyer ──────┘
```

## События приложения

Для взаимодействия слоёв используется общий экземпляр `EventEmitter`.
Модели генерируют события при изменении своих данных.
Компоненты Представления генерируют события при действиях пользователя.
Презентер только обрабатывает события и сам не вызывает `events.emit()`.

## События Моделей данных

### `catalog:changed`

Генерируется Моделью `Catalog` после изменения массива товаров методом `setProducts()`.
Презентер получает товары через `catalog.getProducts()`, создаёт для каждого товара `CardCatalog` и передаёт готовые DOM-элементы компоненту `Gallery`.

### `catalog:selected`
Генерируется Моделью `Catalog` после изменения выбранного товара методом `setSelectedProduct()`.
Презентер получает выбранный товар через `catalog.getSelectedProduct()`, создаёт `CardPreview` и отображает его через `Modal`.

### `basket:changed`
Генерируется Моделью `Basket` после изменения содержимого корзины.
Событие возникает после добавления, удаления или очистки товаров.
Презентер обновляет:

- счётчик `Header`;
- содержимое `Basket`;
- общую стоимость;
- состояние кнопки оформления.

### `buyer:changed`
Генерируется Моделью `Buyer` после изменения или очистки данных покупателя.
Презентер получает данные через `buyer.getData()`, выполняет `buyer.validate()` и обновляет состояние `OrderForm` и `ContactsForm`.

### `basket:open`

После изменения выбранного товара Модель генерирует `catalog:selected`.

### `card:add`

Передаваемые данные:

## Презентер

Презентер отвечает за взаимодействие между Моделями данных и Представлением.
Отдельный класс `Presenter` в приложении не создаётся.
Так как приложение состоит из одной страницы, код Презентера размещается в `src/main.ts`.

## Ответственность Презентера

Презентер отвечает за:

- создание единого экземпляра `EventEmitter`;
- создание экземпляров API;
- создание Моделей;
- создание компонентов Представления;
- первоначальную загрузку каталога;
- подписку на события Моделей;
- подписку на события Представления;
- получение данных из Моделей;
- подготовку данных для компонентов;
- управление каталогом;
- управление выбранным товаром;
- управление корзиной;
- управление формами;
- валидацию данных через Модель `Buyer`;
- формирование объекта `IOrderRequest`;
- отправку заказа;
- отображение результата;
- управление модальным окном.

## Реализация Презентера

В `main.ts` создаётся один экземпляр брокера событий:
- const events = new EventEmitter();
Этот объект передаётся всем Моделям и компонентам View, которым необходим брокер событий.
Презентер не генерирует события самостоятельно.

В `main.ts` отсутствуют вызовы:
events.emit(...)

Презентер только подписывается на события через:
events.on(...)

## Работа Презентера с каталогом

При запуске приложения выполняется запрос:
- webLarekApi.getProducts()
После получения данных вызывается:
- catalog.setProducts(response.items);

Метод Модели генерирует `catalog:changed`.
Презентер обрабатывает `catalog:changed`, получает данные через `catalog.getProducts()` и создаёт карточки `CardCatalog`.

Полные URL изображений формируются с помощью `CDN_URL`.
Полученные DOM-элементы передаются в `Gallery`.
При выборе карточки View генерирует `card:select`.
Презентер вызывает `catalog.setSelectedProduct()`.
Модель генерирует `catalog:selected`.
При обработке `catalog:selected` создаётся `CardPreview` и открывается `Modal`.

## Работа Презентера с корзиной

При `card:add` Презентер получает товар и вызывает:
- basket.addItem(product);
Непосредственного ререндера после этого не происходит.
После изменения Модель генерирует `basket:changed`.
При обработке `basket:changed` обновляются счётчик `Header` и содержимое компонента корзины.
Для подготовки корзины используется отдельная функция `renderBasket()`.
Эта функция вызывается только:
- при обработке `basket:changed`;
- при обработке `basket:open`.
Таким образом соблюдается правило, согласно которому View перерисовывается после изменения Модели либо при открытии модального окна.

## Работа Презентера с данными покупателя

При изменении формы Презентер получает новое значение и вызывает:
- buyer.setData(...)
Модель генерирует `buyer:changed`.
Только после события `buyer:changed` Презентер выполняет:
- buyer.getData();
- buyer.validate();

После этого обновляется состояние `OrderForm` и `ContactsForm`.
View не хранит введённые значения отдельно от Модели.

## Первый этап оформления заказа

При событии `order:open` Презентер получает актуальные данные `Buyer`, выполняет валидацию и отображает `OrderForm`.
При выборе способа оплаты генерируется `order.payment:change`.
При изменении адреса генерируется `order.address:change`.
После каждого изменения данные сохраняются в `Buyer`, который генерирует `buyer:changed`.
При отправке первой формы генерируется `order:submit`.
Презентер отображает `ContactsForm`.

## Второй этап оформления заказа

Изменение email генерирует `contacts.email:change`.
Изменение телефона генерирует `contacts.phone:change`.
Данные сохраняются через `buyer.setData()`.
После изменения `Buyer` генерирует `buyer:changed`, по которому Презентер обновляет форму.
При отправке формы генерируется `contacts:submit`.

## Оформление заказа

При обработке `contacts:submit` Презентер формирует объект `IOrderRequest`.
Данные покупателя получаются через:
- buyer.getData();
Идентификаторы товаров:
- basket.getItems().map((item) => item.id);
Общая стоимость:
- basket.getTotalPrice();
Полученный объект отправляется:
- webLarekApi.createOrder(order);

После успешного ответа Презентер отображает `Success`.
После успешного заказа вызываются:
- basket.clear();
- buyer.clear();
Обе Модели генерируют собственные события изменения данных.

## Управление модальным окном

Презентер передаёт в `Modal` один из самостоятельных компонентов:
- `CardPreview`;
- `Basket`;
- `OrderForm`;
- `ContactsForm`;
- `Success`.

Для открытия используется:
- modal.open();

Для закрытия:
- modal.close();

При действии пользователя `Modal` генерирует `modal:close`, после чего Презентер вызывает `modal.close()`.

## Подготовка данных для Представления

Если компоненту нужны данные из нескольких Моделей, Презентер объединяет их самостоятельно.

Например, при создании `CardPreview` Презентер получает товар из `Catalog` и отдельно проверяет наличие товара в `Basket`:
- const isInBasket = basket.hasItem(product.id);

После этого он формирует данные для компонента:
    preview.render({
        title: product.title,
        price: product.price,
        image: `${CDN_URL}${product.image}`,
        category: product.category,
        description: product.description,
        buttonDisabled: product.price === null || isInBasket,
        buttonText: isInBasket
            ? 'Уже в корзине'
            : 'В корзину'
    });

Модели при этом не изменяются под потребности View.

## Выбранный подход

В проекте используется один Презентер, реализованный непосредственно в `main.ts`.
Файл `main.ts` является точкой сборки приложения:

```text
main.ts
│
├── EventEmitter
├── API
├── Models
├── View
├── обработчики событий Model
├── обработчики событий View
├── подготовка данных
└── первоначальная загрузка
```

Такое разделение соответствует архитектуре `MVP`:

```text
Model
Хранение и изменение данных
        │
        ▼
Presenter
Логика и связь слоёв
        │
        ▼
View
Отображение и пользовательские действия
```

Модели и компоненты Представления не зависят друг от друга напрямую.
